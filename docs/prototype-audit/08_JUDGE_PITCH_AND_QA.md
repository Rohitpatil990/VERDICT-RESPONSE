This document prepares the team to present VERDICT to hackathon judges, run a live demonstration, and answer challenging distributed-systems architecture questions.

## 1. Pitches

### A. The 30-Second Elevator Pitch
> *"In a disaster, communication links fail, but emergency responders cannot stop working. Most distributed systems force a terrible choice: either freeze all operations until global consensus is reached, or accept concurrent updates and silently overwrite life-critical data using Last-Write-Wins timestamps.  
> **VERDICT** introduces Decision-Aware Operational Consistency. Field reports are accepted unconditionally offline without silent overwrites; divisible resources use Escrow bounded counters to prevent over-allocation during partitions; and dispatch decisions pass through a deterministic Decision Gate that gives responders an honest **`GO`**, **`CAUTION`**, or **`HOLD`** verdict based on the real reliability of local data."*

### B. The 2-Minute Technical Deep-Dive
> *"VERDICT partitions data into three semantic classes: Observations, Commitments, and Decisions.  
> 1. **Observations** follow an eventual causal consistency model. Every field report is signed with Ed25519, chained into an append-only SHA-256 operation log, and tracked via causal version vectors. When a partition occurs, regions continue writing locally. Upon reconnection, conflicting updates are detected causally and preserved side-by-side for human reviewer adjudication—never silently clobbered.  
> 2. **Commitments** (such as scarce medical kits or rescue boats) use Escrow bounded counters. We allocate supply quotas per region. Under a partition, each region can safely consume only its local rights, while excess demand queues. Total spent across all partitions is mathematically guaranteed to never exceed capacity, eliminating cross-region coordination during emergencies.  
> 3. **Decisions** evaluate 7 deterministic checks: conflict status, hash-chain integrity, authority reachability, observation freshness, cross-region replication, escrow quota, and confirmation roles. If Mumbai is partitioned from Delhi, Mumbai's territory corridor triggers an authority blind-spot warning.  
> Furthermore, decisions generate cryptographic receipts. When a partition heals and new facts arrive, our **Conflict Blast Radius** re-evaluates past decisions, immediately alerting commanders if a previously approved convoy is now invalidated because the road was revealed to be blocked."*

## 3. Tough Judge Questions & Airtight Technical Answers

### Q1: "Why not just use a standard CRDT with Last-Write-Wins (LWW)?"
> **Answer:** *"Last-Write-Wins relies on physical clock synchronization, which is notoriously unreliable under disaster conditions where NTP servers may be partitioned. More importantly, in emergency response, LWW is actively dangerous: if a volunteer reports a road is OPEN at 10:00:01, and an official sensor reports the bridge collapsed at 10:00:02, a clock skew of just two seconds would cause the bridge collapse report to be silently discarded. In VERDICT, we use causal version vectors to detect true concurrency. Disagreeing claims are preserved side-by-side for human adjudication, while the effective road status defaults to conservative fail-safe BLOCKED."*

### Q2: "Does your system guarantee zero data loss?"
> **Answer:** *"We are very careful with this claim: VERDICT guarantees zero data loss for all **acknowledged writes in our tested persistence and recovery scenarios**. Every local write commits synchronously to the local append-only log before HTTP acknowledgment. However, if an entire host machine suffers physical storage destruction and no peer has received the replicated outbox copy yet, that un-replicated local write cannot be recovered. We do not claim magical cloud durability without multi-machine replication."*

### Q3: "Can we put an AWS Application Load Balancer in front of your regional services to support 100,000 users?"
> **Answer:** *"A standard round-robin or least-connections load balancer cannot be dropped in naively because VERDICT's consistency guarantees are location- and authority-aware. For example, our Escrow system fences spending to the specific region's quota (`EscrowQuotaFenceError`). If an ALB round-robined an escrow request to Delhi instead of Mumbai, it would consume Delhi's medical quota instead of Mumbai's. To scale to 100,000 users, we would deploy an L7 Gateway with **route pinning** for escrow resources, **sticky session affinity** for territory authority, and an edge idempotency cache to protect `PROVE-ONCE` transaction deduplication."*

### Q4: "How do you prevent a malicious node from modifying historical records?"
> **Answer:** *"Every operation includes `prevHash`, forming an append-only SHA-256 hash chain, and is signed with the author region's Ed25519 private key. If someone tampers with a single byte in `mumbai.db.json` (which we demonstrate via our `/admin/tamper` endpoint), the computed SHA-256 hash changes, the hash chain breaks, and signature verification fails immediately (`ent.integrity = 'FAILED'`). The Decision Gate detects this and halts dispatches on that entity until it is healed from an uncorrupted peer."*

### Q5: "What happens if a write times out and the client doesn't know whether it committed?"
> **Answer:** *"This is the two-generals problem in write commitments. Under our **PROVE-ONCE** mechanism, if a client request times out in-flight, `ApiClient` raises an explicit `WriteOutcomeUnknownError` and blocks blind retries. The client then queries our cluster reconciliation endpoint `queryOperationOutcome(clientTxId)`. If any node committed it, it returns `COMMITTED`. If candidate nodes were unreachable, it reports `UNKNOWN`. If the client safely retries with the same `clientTxId`, server deduplication ensures it returns the committed operation without creating duplicate sequence numbers or hash-chain entries."*

### Q6: "Why can't you failover escrow spending to another region if Mumbai is down?"
> **Answer:** *"Because escrow represents physical, divisible assets—such as a finite crate of medical kits physically stored in a Mumbai warehouse. If Mumbai is offline and we silently redirected the spend to Delhi, Delhi would mark its local warehouse inventory as dispatched, creating a physical shortage in Delhi while leaving Mumbai responders without confirmed supplies. By throwing `EscrowQuotaFenceError`, we protect the physical invariant $\sum \text{spent} \le \text{Total}$ by construction."*
